# 03 里程碑与风险

> 这个项目**没有 deadline**。保障机制是「**阶段门**」：
> **每完成一份施工图，就立刻把它实现掉。不允许攒够文档再写第一行代码。**
>
> 每个里程碑必须交出**可运行的产物**

里程碑与 `00-overview.md` 的「交付方式：阶段门」一节一一对应。

## M3 · 能发文（G2）

- 文章 CRUD + 自动保存（30s，乐观锁 + 失败显式告警）
- Markdown 渲染 + 代码高亮
- 发布流程（工作副本 → 发布快照，单事务）
- 拼音 slug 生成 + 手动覆盖
- `/api/v1/export` 导出接口
- 最简管理后台 UI（登录 + 列表 + 编辑器 + **实时预览** + 发布）

> **实时预览为什么必须。**
> 发布到上线有 2–3 分钟延迟（`01` §7.2），预览把「改完想立刻看到效果」和「正式上线」拆成两件事。
> 没有它，改一个错别字都要等 2 分钟才能确认 —— 直接违反「**降低写作门槛是最高优先级**」这条设计原则（`00-overview.md` 的「设计原则」一节）。
> 实现方式见 `01-architecture.md` §4.6。

**通过条件**：能在浏览器里写一篇并发布；`curl /api/v1/export` 能拿到完整内容。

## M8 · RAG 问答（G6）

- ES 混合检索：BM25 + `dense_vector` kNN，**RRF 融合**（不用手调权重）
- 检索 → 重排 → 生成 → **SSE 流式** → **必须带引用来源**
- 语义缓存（相同/相似问题直接命中，控成本）
- 拒答策略：检索不到依据时明确说"我不知道"，**不许编**

## 风险与对冲

| 风险                   | 严重度  | 对冲                                                                                           |
| -------------------- | ---- | -------------------------------------------------------------------------------------------- |
| **内存不足**（ES 方案的头号风险） | 🔴 高 | `-Xmx512m` 卡死 ES、PG `shared_buffers=256m`、0 副本、关 xpack/ml；上线后实测 RSS；逼近上限时**先停 ES**（搜索降级但不致命） |
| **设计做完就结束，代码一行没写**   | 🔴 高 | 阶段门机制：每个门必须交可运行产物；文档与代码交替推进                                                                  |
| **一篇没写**             | 🔴 高 | 每个门结算时检查内容产出；G3 必须发出第一篇                                                                      |
| 范围蔓延                 | 🟡 中 | `00-overview.md` 的「非目标」清单，加功能前先读                                                             |
| ES 索引与发布内容不一致        | 🟡 中 | `es_sync_status` 状态列 + 补偿任务；静态站与 ES 读同一张 `post_publications`                                 |
| LLM 超预算              | 🟡 中 | `ai_usage` 记账 + 语义缓存 + 月预算告警                                                                 |
| 磁盘被图片撑爆              | 🟡 中 | 上传限 5MB + 自动压缩 + 磁盘告警                                                                        |
