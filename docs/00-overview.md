# 00 项目定位与边界

> abyssvstar-blog 是 AbyssvStar 的个人站点

---

## 1. 关于这个项目

- 服务器只有2h4g
- 我会写的文章很少，也没有文笔

所以影响到后续一些决策

---

## 2. 非目标

| 不做 | 理由 |
|------|------|
| ❌ 多用户 / 注册 / RBAC | 只有我一个作者 |
| ❌ 评论嵌套回复 | 第一版只做最简留言板 |
| ❌ 消息队列（Kafka / RabbitMQ） | 没有跨进程事件，"DB 状态表 + 定时任务"足够 |
| ❌ CQRS / 事件驱动 / Outbox | 领域逻辑太薄，读写同库足够。完整论证见 `01-architecture.md` §7.1.2 |
| ❌ 分布式锁 / 分库分表 | 没有这个量级的问题 |
| ❌ 内容形态全做（专栏/收藏/笔记） | 第一版只做「文章 + 短动态」 |

---

## 3. 交付方式：阶段门，而不是时间表

这个项目**没有 deadline**，所以保障机制换成「**阶段门**」：

> **每完成一份施工图，就立刻把它实现掉。不允许攒够 10 篇文档再写第一行代码。**

### 阶段门清单

| 门 | 通过条件（必须是可运行、可验证的产物） |
|---|---|
| **G0 设计定稿** | `docs/` 各章施工图写完，每条决策都有"为什么不选别的" |
| **G1 骨架跑起来** | `docker compose up` 起 PG/Redis/app；Flyway 迁移通过；能登录后台 |
| **G2 能发文** | 后台能写、能发布；`/api/v1/export` 能拿到完整内容 |
| **G3 能上线** | 静态站构建通过；Nginx + HTTPS 可访问；**后台实时预览可用**（静态方案的发布延迟靠它补偿，见 `01` §4.6）；**第一篇文章公网可见** |
| **G4 搜得到** | ES 索引建立；搜索可用；**停掉 ES 仍能搜**（降级到 PG） |
| **G5 用得上 AI** | 写作助手（摘要/标签/相关旧文）可用；`ai_usage` 记账准确 |
| **G6 问得动** | RAG 问答流式返回且**带引用来源** |
| **G7 活得久** | 备份**恢复演练**通过；内存/磁盘告警生效 |

**每个门都必须交出可运行的产物，不允许"文档写完就算过"。**

### 长期标准

- 服务器内存峰值 < 2.8GB（含 MinIO 与 ES，上线后实测校准回填）
- 能在手机浏览器上发一条短动态

## 4. 设计原则

1. **为演化而设计** —— 初版把扩展边界留好，功能等真遇到问题再加。
2. **降低写作门槛是最高优先级** —— 不要让"写"变麻烦。
3. **AI 必须可降级** —— AI 不可用时，整个站必须完全正常。
   **但这条只管"可选增强"，不管核心依赖**：PostgreSQL / Redis / MinIO 不可用时，
   应用**直接启动失败**而不是降级运行。判据（「变差」还是「不成立」）见 `01-architecture.md` §5。
