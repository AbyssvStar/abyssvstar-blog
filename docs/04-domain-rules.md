# 04 业务规则与领域模型（施工图）

---

## 1. 核心概念

| 概念       | 含义                                                                                  |
| -------- | ----------------------------------------------------------------------------------- |
| **工作副本** | `posts` 表。在后台编辑的内容，可以被自动保存反复改写，**不直接上线**                                            |
| **发布快照** | `post_publications` 表。点「发布」那一刻的内容，**不可变，静态站和 ES 都只读它**                              |
| **对外可见** | `status = PUBLISHED AND visibility = PUBLIC AND published_at <= now()`，**这是唯一判定真源** |
| **构建**   | 静态站重新生成。只在"发布快照发生变化"时触发，有 30s 防抖                                                    |

---

## 2. 为什么必须有"工作副本 / 发布快照"的分离

- **服务端自动保存（每 30s）**
- 同时要求「**发布才上线**」

如果自动保存直接改的就是线上内容，那么：改了半句话 → 30 秒后自动保存 → 内容变了 → 静态站构建时读到的是这半句 → **未完成的修改直接上线了**。

所以工作副本和发布快照**必须分开**。

| 方案                               | 评价                                             |
| -------------------------------- | ---------------------------------------------- |
| `posts` 里加一堆 `published_*` 列     | 表变宽；标签、封面、slug 都要各自的快照列，很快失控                   |
| **`post_publications` 快照表（选这个）** | 一张表装下所有已发布形态；标签用 `jsonb`；静态导出和 ES 索引读同一张表，天然一致 |
| 每次发布存一条历史版本                      | 那是修订历史，会一直涨                                    |

> `post_publications` 与 `posts` 是 **1:1**（`UNIQUE(post_id)`），只保留最新一次发布。**它是"发布语义"，不是 CQRS 读模型**——没有独立服务、没有事件同步、没有最终一致性窗口。

## 3. 文章状态机

### 3.1 两个正交维度

```
status（生命周期，单选）          visibility（可见性，单选）
  DRAFT       草稿                  PUBLIC   公开
  SCHEDULED   已排期                PRIVATE  私密（只在后台可见）
  PUBLISHED   已发布
  ARCHIVED    已归档
```

**为什么正交而不是塞进一个枚举**：这样"私密笔记"可以是 `DRAFT + PRIVATE`（还没写完的私人笔记），也可以是 `PUBLISHED + PRIVATE`（写完并"发布"了、但只我自己看的笔记）。语义清晰，状态迁移不重复。

### 3.2 状态迁移

```
        ┌──────────┐  设 publish_at（未来）  ┌────────────┐
        │  DRAFT   │ ─────────────────────→ │ SCHEDULED  │
        └────┬─────┘                        └─────┬──────┘
             │ 直接发布                            │ 到点（定时任务）
             │                                    ▼
             │                             ┌────────────┐
             └───────────────────────────→ │ PUBLISHED  │
                                           └─────┬──────┘
                     取消排期 / 退回草稿          │ 归档
             ┌───────────────────────────────────┤
             ▼                                   ▼
        ┌──────────┐                        ┌──────────┐
        │  DRAFT   │ ←───────────────────── │ ARCHIVED │
        └──────────┘        取消归档         └──────────┘
```

| 规则 | 说明 |
|------|------|
| `DRAFT → SCHEDULED` | 必须提供**未来**的 `publish_at`，否则报 `PUBLISH_TIME_IN_PAST` |
| `DRAFT → PUBLISHED` | 立即发布，`published_at = now()` |
| `SCHEDULED → PUBLISHED` | 只由定时任务执行，不由人工触发 |
| `SCHEDULED → DRAFT` | 取消排期，清空 `publish_at` |
| `PUBLISHED → ARCHIVED` | 保留快照，从所有列表和 sitemap 消失；`/posts/{slug}` 返回 410 |
| `ARCHIVED → PUBLISHED` | 恢复，重建快照并触发构建 |
| **`PRIVATE` 文章不参与以上任何"触发构建"的逻辑** | 私密内容不进静态构建，改了也不重建站 |

### 3.3 私密文章的确切边界（重要）

因为「只在后台可见 / 可搜 / 可编辑」。落地为**四条硬规则**：

1. `visibility = PRIVATE` 的文章**永不写入** `post_publications`
2. 它**永不进** `/api/v1/**` 的任何端点（包括导出、搜索、RSS、sitemap）
3. 它**永不进** ES 的公开索引（要搜就在后台走 PG 的 `pg_trgm` 或单独一个 private 索引）
4. 后台搜索时明确标注「私密」，**绝不能**在后台的列表里把它和公开文章混排而不加标记

> 第 4 条是防"自己看错"的。第 1–3 条是防泄漏的：**任何一条没做到，就等于把私人笔记挂在了公网上。**

## 4. 发布流程（施工级）

```
POST /admin/api/posts/{id}/publish
┌─ 校验 ───────────────────────────────────────────────┐
│  · title 非空                                        │
│  · content_md 非空                                   │
│  · slug 唯一（排除自己，且排除已归档的）              │
│  · 标签 ≤ 5 个且都存在                               │
│  · visibility=PUBLIC 时：summary 非空（SEO 需要）     │
└──────────────────────────────────────────────────────┘
┌─ 单事务（必须全成功或全失败）──────────────────────┐
│  1. html = renderMarkdown(content_md)                │
│  2. word_count / reading_minutes = 统计(html)         │
│  3. UPSERT post_publications ON CONFLICT (post_id)    │
│       (slug, title, summary, html, cover_url,         │
│        tags jsonb, source_hash, published_at)         │
│  4. posts.status = PUBLISHED                          │
│  5. INSERT site_builds(reason, status = PENDING)      │
└──────────────────────────────────────────────────────┘
┌─ 事务提交后（失败不影响发布成功）──────────────────┐
│  a. 异步推 ES 索引；失败 → es_sync_status = FAILED    │
│  b. 由定时任务统一合并触发构建                        │
└──────────────────────────────────────────────────────┘
```

### 4.1 "有未发布修改"怎么判定

```
has_unpublished_changes = sha256(title + summary + content_md + slug + tags + cover)
                          ≠ post_publications.source_hash
```

后台列表上直接显示一个圆点，提醒"这篇有改动还没上线"。**这是自动保存能安全存在的前提。**

## 5. 自动保存规则

| 规则       | 值                                            |
| -------- | -------------------------------------------- |
| 触发       | 编辑器内容变化后 **30 秒**无新输入                        |
| 接口       | `PATCH /admin/api/posts/{id}`，只写工作副本         |
| 副作用      | **不触发构建、不碰发布快照、不推 ES**                       |
| 冲突       | 带 `version` 乐观锁；版本不匹配返回 `409`，前端提示"内容已在别处修改" |
| **失败处理** | 自动保存失败时，**前端必须显式报警**（红点 + 文案"未保存"），绝不允许静默失败  |

> **服务端保存失败就是唯一的丢稿风险**。因此保存成功时应该显示"已保存 HH:mm:ss"，让人安心。

## 6. 定时发布规则

```
@Scheduled(fixedDelay = 60s)
  SELECT * FROM posts
   WHERE status = 'SCHEDULED' AND visibility = 'PUBLIC' AND publish_at <= now()
   FOR UPDATE SKIP LOCKED
  → 逐条执行与手动发布完全相同的流程（复用同一段代码）
```

| 边界场景 | 处理 |
|---------|------|
| 服务器停机跨过了 `publish_at` | 重启后下一次扫描立即发布，**不会漏**（因为判断条件是 `<= now()` 而非"刚好等于"）|
| 同一秒有多篇到期 | `FOR UPDATE SKIP LOCKED` + 逐条发布，最后合并成一次构建 |
| 定时任务重复执行 | 发布流程以 `status` 为幂等键：已经是 `PUBLISHED` 就跳过 |
| 排期时文章被改为 `PRIVATE` | 扫描条件带 `visibility = 'PUBLIC'`，直接跳过 |

## 7. 短动态（notes）规则

| 规则   | 值                                                |
| ---- | ------------------------------------------------ |
| 内容   | 纯文本，**不支持 Markdown**（保证"随手发"的心理成本最低）             |
| 长度   | ≤ 500 字                                          |
| 图片   | 可选，最多 4 张，存 `note_assets`，有顺序                    |
| URL  | `/notes/{id}`（**不用 slug** —— 动态不值得为 URL 好看多一步操作） |
| 草稿分离 | **不做**。动态是即时媒介，没有长草稿过程；编辑后直接改内容并触发构建             |
| 状态   | 只有 `PUBLISHED` / `ARCHIVED`，没有 `SCHEDULED`       |
| 可见性  | 同样支持 `PUBLIC` / `PRIVATE`（私密动态 = 私人速记）           |

> 动态的图片必须走和文章图片同一条上传管线（`assets` 表），只是用 `note_assets` 记录顺序。

## 8. 标签规则

| 规则       | 值                                |
| -------- | -------------------------------- |
| 每篇上限     | **5 个**（前后端双重校验）                 |
| 单个标签长度   | 1–20 字                           |
| 新建       | 打标时若不存在则自动创建，`slug` 由拼音生成        |
| **删除标签** | **只删标签和关联，文章一律不动**               |
| 空标签      | 定时任务每天清理，只清"0 篇文章关联"且"创建超过 7 天"的 |
| 合并       | 第一版不做，手动改名即可                     |
| AI 推荐    | 推荐结果只作为**建议**填入编辑框，**必须人工确认**才写入 |

---

## 9. 阅读量规则

| 规则  | 值                                                                                                         |
| --- | --------------------------------------------------------------------------------------------------------- |
| 打点  | `POST /api/v1/views`，body `{type, id}`                                                                    |
| 去重  | Redis key `view:{type}:{id}:{ipHash}`，TTL **1 小时**（同一 IP 一小时内只算一次）                                        |
| 计数  | Redis `INCR view:count:{type}:{id}`                                                                       |
| 落库  | 定时任务每 5 分钟：把 Redis 增量写入 `daily_views(date, type, id, count)`，并累加到 `posts.view_count` / `notes.view_count` |
| 落库后 | 用 `DECRBY` 减去已落库增量，**不用 DEL**（避免丢并发期间的计数）                                                                 |
| 防刷  | 同 IP 小时去重 + 单 IP 全站每小时 ≤ 100 次打点；超限静默丢弃（不报错，不给爬虫反馈）                                                       |
| 隐私  | **只存 `ip_hash`（盐值哈希），绝不存原始 IP**                                                                           |
| 展示  | 文章页显示阅读量；后台可看趋势（`daily_views` 按天聚合）                                                                       |

> 打点接口必须是**幂等且永不报错**的：任何异常都吞掉并返回 204。它不能影响读者体验，也不能成为攻击面。

## 10. 删除语义

| 对象  | 语义                                                   |
| --- | ---------------------------------------------------- |
| 文章  | **软删除**（`deleted_at`）。列表、搜索、导出全部过滤。同时**删除发布快照**并触发构建 |
| 短动态 | 软删除，同上                                               |
| 图片  | **不立即删文件**。软删除记录 + 定时任务检查"7 天内无引用则物理删除"              |
| 留言  | 硬删除（`SPAM` 除外——保留用于 IP 封禁统计）                         |
| 标签  | 关联先删，标签留待定时清理                                        |

**为什么文章软删除但发布快照删掉**：软删除是为了误删可恢复（工作副本还在），发布快照删掉是为了**立刻从线上消失**。

## 11. 构建触发的完整规则

**只有以下事件触发构建：**

| 事件                     | 触发                          |
| ---------------------- | --------------------------- |
| 文章发布 / 更新线上 / 归档 / 恢复  | ✅                           |
| 短动态发布 / 编辑 / 归档        | ✅                           |
| 站点配置修改（标题、导航、关于页）      | ✅                           |
| **自动保存**               | ❌                           |
| **私密文章任何改动**           | ❌                           |
| **留言审核通过 / 驳回 / 标记垃圾** | ❌（评论由前端 JS 动态获取，重建站也看不到新评论） |
| **标签改名（不改文章）**         | ❌（标签页在下次构建时自然更新）            |
| **阅读量变化**              | ❌（前端 JS 动态获取，不进静态 HTML）     |

**防抖**：定时任务每 10s 检查，若有 `PENDING` 且距上次 `FIRED` > 30s，合并成一次 `repository_dispatch`。

> 判断标准只有一条：**作者写的东西进 HTML，读者写的东西走接口。**
>
> - **文章、短动态是作者写的** —— 只在发布时变，进静态 HTML，换来 SEO 与最快首屏
> - **评论、阅读量是读者产生的** —— 随时在变，必须走客户端 fetch

## 12. 对外可见性的判定真源

任何"这条内容能不能被访客看到"的判断，**只能来自这一个条件**：

```sql
status = 'PUBLISHED'
  AND visibility = 'PUBLIC'
  AND deleted_at IS NULL
  AND (published_at IS NOT NULL AND published_at <= now())
```

**这条 SQL 必须只出现在一个地方**（一个 `PublishedContentSpec` 之类的封装），任何地方要判断可见性都调它。**散落多处判定 = 迟早泄漏私密内容。**
